# راهنمای گردش کار Git/GitHub و معماری استقرار روی سرور Ubuntu 24.04 (4 vCPU / 8GB RAM)

این سند استانداردهای عملیاتی توسعه در لوکال (`d:\project\hami3`)، نسخه‌بندی در GitHub و معماری استقرار نهایی روی سرور اوبنتو ۲۴ را مطابق بخش ۲۳ سند PRD (`OPS-001` تا `OPS-013`) و گیت `Exact-Build Owner Handoff` (بند ۱۸.۱ فرمانده) مشخص می‌کند.

---

## ۱. استراتژی توسعه در لوکال و نسخه‌بندی روی GitHub

### ۱.۱. ساختار شاخه‌ها (Branching Strategy)
- `main`: شاخه پایدار و آماده انتشار (Production-Ready). هر کامیت روی این شاخه باید دارای تگ نسخه (مثلاً `v1.0.0-rc1`, `v1.0.0`) و هش ساخت (`BUILD_ID`) مشخص باشد.
- `develop`: شاخه تجمیع فازهای توسعه پس از پاس شدن تست‌ها و ممیزی مستقل Qwen/GLM.
- `feat/phase-<N>-<topic>`: شاخه‌های کاری برای هر تسک (مثلاً `feat/phase-2-auth-rbac`, `feat/phase-5-doctor-visits`).
- `fix/<issue-id>`: شاخه‌های رفع باگ با حداقل تغییر ممکن (`Minimal Change`).

### ۱.۲. قوانین کامیت و ردیابی (Traceability)
هر کامیت باید به شناسه تسک فرمانده و نیازمندی PRD اشاره کند تا زنجیره `Requirement → Task → Commit → Build` صددرصد قابل ردیابی باشد:
- مثال: `feat(visit): enforce row-level lock on membership quota [TASK-05.3][VISIT-005][AC-07]`
- هیچ فایل حاوی رمز یا کلید واقعی (`.env`, کلیدهای خصوصی بکاپ) هرگز وارد گیت نمی‌شود (`.gitignore` سخت‌گیرانه).

### ۱.۳. پایپ‌لاین GitHub Actions (CI)
در هر Push یا Pull Request به `develop` و `main`:
1. بررسی Typecheck و Lint.
2. بالا آمدن سرویس‌های PostgreSQL 16 و Redis 7 در کانتینر CI.
3. اجرای Migrationها و بررسی صحت Schema.
4. اجرای تست‌های واحد و **تست‌های هم‌زمانی (Concurrency Tests برای AC-07, AC-12, AC-15)**.
5. اجرای تست‌های E2E و ثبت هش دقیق نسخه (`SOURCE_FINGERPRINT` و `BUILD_ARTIFACT_HASH`).

## ۲. بودجه‌بندی منابع سرور Ubuntu 24.04 LTS (4 vCPU / 8 GB RAM)

برای اینکه سرور ۸ گیگابایتی در ترافیک بالا یا هنگام بکاپ‌گیری شبانه هرگز دچار کمبود حافظه (OOM Kill) نشود، منابع به شکل زیر در `docker-compose.prod.yml` قفل می‌شوند:

| سرویس / بخش | سهم RAM اختصاصی (Hard Limit) | سهم CPU | توضیحات تنظیم بهینه |
|---|---|---|---|
| **سیستم‌عامل Ubuntu 24.04 + Kernel Cache** | ~1.5 GB | 0.5 Core | به همراه 4 GB فضای Swap روی دیسک NVMe/SSD با `vm.swappiness=10` |
| **PostgreSQL 16 (Database)** | **2.5 GB** | 1.5 Cores | `shared_buffers=640MB`, `effective_cache_size=1800MB`, `work_mem=16MB`, `max_connections=100` |
| **اپلیکیشن حامی‌کارت (App / API + SSR)** | **2.5 GB** | 1.5 Cores | اجرای Node.js با `NODE_OPTIONS="--max-old-space-size=2048"` |
| **Redis 7 (Session, Rate-Limit, Queue)** | **512 MB** | 0.25 Core | `maxmemory 400mb`, `maxmemory-policy volatile-lru`, `appendonly yes` |
| **Caddy / Nginx (Reverse Proxy + SSL)** | **256 MB** | 0.25 Core | فشرده‌سازی Zstd/Gzip، مدیریت گواهی TLS خودکار، هدرهای امنیتی |
| **فضای آزاد ضربه‌گیر (Headroom & Backup Cron)** | **~750 MB** | اشتراکی | برای اجرای روان `pg_dump` و رمزنگاری شبانه بدون فشار به سرویس اصلی |

## ۳. پروتکل پشتیبان‌گیری رمزنگاری‌شده و بازیابی آزمایشی (OPS-001..010)

طبق الزامات **P0** در بخش ۲۳ PRD (`OPS-003`, `OPS-004`, `OPS-005`, `OPS-006`) و سناریوی پذیرش `AC-16`:

1. **بکاپ خودکار شبانه (`ops/backup.sh`):**
   - تهیه Snapshot سازگار از دیتابیس با `pg_dump --format=custom --no-owner`.
   - بسته‌بندی فایل‌های مدارک بارگذاری‌شده نمایندگان و پزشکان (`uploads/private_documents`).
   - **رمزنگاری قوی پیش از خروج از سرور** با استفاده از `age` یا `gpg` (کلید عمومی کارفرما) به‌طوری که فایل بکاپ بدون کلید خصوصی مطلقاً قابل خواندن نباشد (`OPS-005`).
   - ارسال خودکار نسخه رمزنگاری‌شده با `rclone` به پوشه اختصاصی **Google Drive کارفرما** (`OPS-004`) + چرخش نسخه‌ها (نگهداری ۷ نسخه روزانه، ۴ نسخه هفتگی، ۶ نسخه ماهانه).
2. **حفظ کلید رمزگشایی اطلاعات بانکی (`OPS-006`):**
   - کلید رمزنگاری فیلدهای حساس (یا کلید اصلی محیط) در یک گاوصندوق رمزنگاری‌شده مستقل تحویل مالک محصول می‌شود تا پس از بازیابی، اطلاعات بانکی و شبا برای نقش‌های مجاز قابل استفاده باقی بماند.
3. **آزمون اجباری بازیابی (`Restore Drill — AC-16`):**
   - پیش از تحویل نهایی، یک دیتابیس آزمایشی خالی ساخته می‌شود، بکاپ رمزنگاری‌شده از Google Drive دانلود و رمزگشایی شده و درون آن بازیابی می‌شود.
   - اسکریپت صحت‌سنجی (`ops/verify-restore.sh`) بررسی می‌کند که تعداد کاربران، عضویت‌ها، جمع مانده کیف پول‌ها و امکان مشاهده شبا توسط `SUPER_ADMIN` دقیقاً با قبل از بکاپ برابر باشد.

## ۴. استقرار بدون قطعی و بازگشت سریع (Safe Rollout & Rollback — OPS-007..010)

1. هر نسخه جدید با تگ گیت مشخص (`IMAGE_TAG=v1.x.y`) ساخته می‌شود و ایمیج نسخه قبلی روی سرور حفظ می‌گردد (`OPS-010`).
2. پیش از اجرای Migration در پروداکشن، اسکریپت به صورت خودکار یک بکاپ فوری (`pre-deploy-snapshot`) می‌گیرد.
3. Migrationهای دیتابیس فقط به صورت **Backward-Compatible (غیرمخرب)** نوشته می‌شوند (`OPS-007`).
4. پس از بالا آمدن کانتینر جدید، اسکریپت `smoke-check` سلامت سرویس، دیتابیس و صفحات اصلی را بررسی می‌کند (`OPS-008`). اگر خطایی رخ دهد، اسکریپت به صورت خودکار کانتینر را به `IMAGE_TAG` قبلی برمی‌گرداند (`OPS-009`).
